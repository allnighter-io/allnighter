**Why the capacity receipt is the load-bearing evidence.** §7's
`PATH -> vendor availability` ban requires scheduler spawns to use resolved
absolute invocations, because launchd's PATH is a fallback only. The daemon runs
with the minimal PATH above — no login shell, no Homebrew, no user PATH.
`capacityRefresh` spawns real vendor CLIs. Its `lastSuccessAt` advancing inside
that daemon is therefore direct evidence that a persisted absolute vendor
invocation works under launchd's minimal PATH, which is exactly item 5's claim.

## The assertion had to be made able to fail, three times

Recorded because the gate passed twice for the wrong reason before it passed for
the right one.

1. **Failed wrongly.** `probeRecordRefresh` was called *stuck* when it had woken,
   found no work and re-armed. `ProbeRecordRefreshScheduler.shouldSmoke` returns
   false while probe records are fresher than the 30-minute
   `ProbeFreshnessGate.gateInterval`, and the loop then re-arms without recording
   an attempt.
2. **Passed wrongly.** With a 120 s observation window, `capacityRefresh`'s
   ~5-minute deadline never fell inside it, so the one load-bearing assertion was
   *skipped* and reported as a PASS. The gate could not fail. A skipped
   assertion now fails with "gate 5 unproven, not passed".
3. **Failed wrongly again.** With the assertion running, a 15 s grace failed a
   healthy scheduler: `capacityRefresh` with `nextWakeAt` 20:14:49 attempted at
   20:15:05 (16 s late — poll tick plus jitter) and recorded success at 20:15:15
   (26 s late — the vendor spawn takes ~10 s). Grace is now 90 s, and the
   measurement is recorded at the constant.

## Observability gap found, not fixed

A scheduler that woke, found nothing due, and re-armed is **indistinguishable in
the receipts from one that never ran**: `lastAttemptAt: null`,
`lastSuccessAt: null`, `lastError: null`, `state: "waiting"`. §6 lists
registered / running / waiting / failed and has no "idle, nothing due". A reader
cannot tell healthy-and-idle from never-started.

The harness works around it by classifying from `nextWakeAt` movement. The
underlying receipt schema is unchanged; whether §6 should gain an idle state is
an open question, deliberately not answered here.

## What this does NOT prove

- One host, one moment, ad-hoc track.
- `probeRecordRefresh` was idle for most of the observation window; its vendor
  path is not separately proven here, only `capacityRefresh`'s.
- The plist PATH is asserted against one known-bad entry (`/opt/homebrew/bin`),
  not against every possible login-shell path.
- §10.1 R1 untouched.
