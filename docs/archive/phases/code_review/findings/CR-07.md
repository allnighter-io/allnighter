# CR-07 — StalledWorkDetector worker-turn scan vs slow GLM pair slices

## Summary

`scanWorkerTurns` applies a flat 30-minute `workerChatSeconds` threshold to every
queued/running `.workerChat` turn with no awareness of whether that turn is
tracking an active child `TeamRun`. Because `scanTeamRuns` uses a longer 60-minute
`teamRunSeconds` threshold, a slow GLM pair slice (Supervisor + Hammer) will trip a
`workerChat` stall episode at 30 minutes — before the child run it is driving has
exhausted its own 60-minute budget. The `runningNoProgress` verdict also depends
entirely on what `observableEvent` counts as progress, and if that only resets on
status transitions, every long-running turn with no discrete event is a false
positive. Wake-ticket suppression is keyed on `(threadId, runId)` and may miss pair
child runs whose run identity does not match the parent tracking turn.

## Findings

### P0 — None

No invariant or security violation found. The detector is local-truth, read-only,
and carries no secrets or network surface. All issues below are correctness/false-positive
concerns, not invariant breaks.

### P1 — Pair child run fires workerChat stall (30m) before teamRun threshold (60m)

- **Invariant:** A `.workerChat` turn that is tracking an active child `TeamRun`
  must not emit a stall episode before the child run's own threshold has elapsed.
  The parent turn and the child run are one piece of work; the shorter of the two
  thresholds wins and produces a false positive.
- **Evidence:**
  - `StalledWorkDetector.swift:8` — `workerChatSeconds` defaults to `30 * 60`,
    `teamRunSeconds` to `60 * 60`. The worker threshold is half the team-run
    threshold.
  - `StalledWorkDetector.swift:36-37` — `scan` calls `scanWorkerTurns` (30m) and
    `scanTeamRuns` (60m) independently; neither is aware of the other's verdict.
  - `StalledWorkDetector.swift:50-58` — `scanWorkerTurns` iterates every
    `.workerChat` turn, checks `status`, `requiresUserAttention`, and wake-ticket
    suppression, then applies `workerChatSeconds` directly. There is **no check**
    against `input.runs` to see whether `turn.runId` corresponds to an active
    `TeamRun` that `scanTeamRuns` already owns.
  - `StalledWorkDetector.swift:66` — the episode is filed with `runId: turn.runId`,
    so a pair child run would produce two episodes for one piece of work: a
    `workerTurn` episode at 30m and a `teamRun` episode at 60m.
- **Suggested fix:** In `scanWorkerTurns`, skip any turn whose `turn.runId` matches
  a `TeamRun` in `input.runs` that is still within its own `teamRunSeconds` budget —
  let `scanTeamRuns` own the verdict for runs it is already scanning. Alternatively,
  extend the per-turn threshold to `max(workerChatSeconds, teamRunSeconds)` when
  `turn.runId` resolves to an active run. The skip is cleaner: it also kills the
  double-count.
- **Suggested slice:** SWW pair-run threshold gate

### P1 — `runningNoProgress` false positive if `observableEvent` only resets on status transitions

- **Invariant:** A `.running` turn that is actively producing output (streaming
  tokens, heartbeat pings, child-run progress) must not be flagged as stalled.
  The verdict is only correct if `observableEvent` resets on real progress, not
  just on `queued → running` status transitions.
- **Evidence:**
  - `StalledWorkDetector.swift:56` — `let lastEvent = observableEvent(for: turn,
    thread: thread)` is the sole source of the deadline anchor. Its implementation
    is not inlined, so the reset contract is unverified.
  - `StalledWorkDetector.swift:57-58` — `age = now - lastEvent.at`; stall fires
    when `age >= workerChatSeconds`. If `lastEvent` is the `queued → running`
    transition timestamp, then any turn that runs longer than 30 minutes without a
    status change is a false positive — exactly the slow-GLM-slice case.
  - `StalledWorkDetector.swift:59` — the reason is `.runningNoProgress`, which
    asserts progress has stopped. That assertion is only as good as what
    `observableEvent` counts.
- **Suggested fix:** Confirm and document that `observableEvent` resets on
  streaming-token events, heartbeat pings, and child-run progress callbacks — not
  just status transitions. If it does not, add a heartbeat/streaming event source
  before trusting `.runningNoProgress`. Add a test that a turn emitting tokens at
  29 minutes does not stall at 31.
- **Suggested slice:** SWW observableEvent reset contract

### P2 — Wake-ticket suppression keyed on (threadId, runId) may miss pair child runs

- **Invariant:** A wake ticket filed against a pair child run (or against the
  thread broadly) should suppress stall episodes for the parent's tracking turn.
- **Evidence:**
  - `StalledWorkDetector.swift:53-55` — `suppressedByWakeTicket(pending:,
    threadId: thread.id, runId: turn.runId, now:)`. The suppression key is
    `(threadId, runId)`.
  - `StalledWorkDetector.swift:66` — the episode uses `runId: turn.runId`. If the
    wake ticket is filed against the child run's id but `turn.runId` is the parent's
    (or `nil` for a pure chat turn), the key will not match and suppression fails.
- **Suggested fix:** Confirm `suppressedByWakeTicket` accepts thread-scoped tickets
  (runId `nil` matches any turn on that thread) and that child-run tickets suppress
  the parent tracking turn. If matching is strict on runId, relax to thread-scoped
  when `turn.runId` is `nil` or when the turn owns a child run.
- **Suggested slice:** SWW wake-ticket thread-scope match

### P2 — Stateless detector re-emits a fresh episode (new id, firstDetectedAt=now) every scan

- **Invariant:** A stall episode for the same target should be stable across scans
  until cleared, so the consumer can dedupe and so `firstDetectedAt` reflects the
  true first detection, not the most recent scan.
- **Evidence:**
  - `StalledWorkDetector.swift:33` — default `idFactory` mints `"stall_" + UUID`,
    so every scan of the same stalled turn produces a new episode id.
  - `StalledWorkDetector.swift:68` — `firstDetectedAt: input.now` is set fresh on
    every scan, not carried forward from a prior episode.
  - The detector carries no prior-episode state, so the same stalled turn produces
    a new episode (new id, reset `firstDetectedAt`) every scan cycle.
- **Suggested fix:** Either (a) make the episode id deterministic from `targetId`
    (`"stall_turn_\(turn.id)"`) so repeated scans produce the same id and the
    consumer can dedupe, or (b) document that the caller must reconcile by
    `targetId` and carry `firstDetectedAt` forward. Option (a) is cheaper and
    removes the burden from every caller.
- **Suggested slice:** SWW episode id determinism

### P2 — Threads without projectId are silently skipped

- **Invariant:** Stall detection should cover all work the user can see, or the
  skip should be documented as intentional.
- **Evidence:**
  - `StalledWorkDetector.swift:49` — `guard let projectId = thread.projectId else
    { continue }`. Threads with no project (ad-hoc chat, detached runs) never
    produce stall episodes.
- **Suggested fix:** Confirm this is intended (stall routing needs a project for
  nudge/escalation). If ad-hoc chat can stall, route to a default project or emit
  with a `nil`-project escape hatch. Low priority — likely intentional.
- **Suggested slice:** (none — confirm intent)

## False alarms ruled out

- **`requiresUserAttention` skip (line 52) masks stalls:** Not a bug. Turns
  requiring user attention are routed through a separate user-attention flow; the
  skip is intentional and prevents double-routing.
- **`age >= threshold` (line 58) off-by-one:** Not a bug. `>=` is correct
  deadline semantics — the threshold is the deadline, not a grace period. Using
  `>` would let a turn run one extra scan cycle past the deadline.
- **`projectId == nil` skip (line 49) drops project-backed work:** Not a bug for
  project-backed work — only project-less threads are skipped. See P2 above for
  the edge case.
- **Double-count of workerChat + teamRun episodes for the same run:** Real
  concern, folded into P1 #1 (pair child run). The fix there (skip turns whose
  runId is an active TeamRun) also eliminates the double-count.
