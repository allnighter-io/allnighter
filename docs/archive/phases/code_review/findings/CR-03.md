# CR-03 — SliceGate scope and danger enforcement

## Summary
`SliceGate.evaluate` correctly blocks on `dangerFlags`, requires a non-empty
`touchAllowlist`, and validates all four executor facts (`exists`, `isMutating`,
`isRunnable`, `workerCount == 1`). No P0 bypass was found: nil packet, empty
`sliceId`/`intent`, and any danger flag all fail closed. The real weaknesses are
(1) the gate checks only *presence* of `touchAllowlist`, not per-entry validity or
path containment, so degenerate entries like `[""]` or `["../etc/passwd"]` pass;
(2) the `default: break` in the check-method switch silently allows unknown or
newly added check methods without validating their payload; (3) the gate does not
correlate the packet with the executor identity, so a mismatched packet/executor
pair is not detected; and (4) the gate is a static pre-check while actual
scope enforcement (touches-within-allowlist) is deferred to runtime, which is an
architectural gap if runtime enforcement is absent or buggy.

## Findings

### P0 — None found
No invariant/security bypass identified. The gate blocks on danger
(`SliceGate.swift:22-25`), requires `touchAllowlist` non-empty
(`SliceGate.swift:33-34`), and validates all four executor facts
(`SliceGate.swift:44-54`). Nil packet is blocked (`SliceGate.swift:19-21`); empty
`sliceId`/`intent` blocked (`SliceGate.swift:27-31`); nil `check.command`/
`check.fixture` handled via `?? ""` and blocked when empty
(`SliceGate.swift:37-40`).

### P1 — `touchAllowlist` entries not validated; degenerate entries pass
- **Invariant:** `touchAllowlist` must declare real, in-scope paths for mutating
  units. The doc comment calls this a "scope gate," so scope must mean more than
  "array has count >= 1."
- **Evidence:** `SliceGate.swift:33-34` — `guard !packet.touchAllowlist.isEmpty
  else { ... }` checks only array emptiness.
- **Impact:** `[""]`, `["   "]`, `["../etc/passwd"]`, and `["/etc/passwd"]` all
  pass the gate. A mutating slice with a whitespace-only or path-escaping
  allowlist is admitted as "safe."
- **Suggested fix:** Validate each entry is non-empty after trim; reject
  path-escaping entries (`..` components, absolute paths outside repo root). At
  minimum, reject all-whitespace entries so `[""]` no longer passes.
- **Suggested slice:** SliceGate: validate touchAllowlist entries

### P1 — `default: break` silently allows unknown check methods
- **Invariant:** every `check.method` case must validate its payload or be
  explicitly allow-listed. A new case added to the enum should fail closed, not
  open.
- **Evidence:** `SliceGate.swift:36-43` — the switch only blocks for `.command`
  with empty command and `.guiFixture` with empty fixture; `default: break`
  (`SliceGate.swift:41-42`) admits every other case with no payload check.
- **Impact:** If a `.manual`/`.none`/`.skip` case exists, a mutating slice with
  no automated check passes the gate. If a new case (e.g., `.snapshot`) is added
  later, it silently bypasses check validation with no compile-time signal.
- **Suggested fix:** Replace `default: break` with explicit cases for any
  intentionally check-less methods (e.g., `.manual`), and add
  `@unknown default` that returns `.blocked(...)` so future cases fail closed.
- **Suggested slice:** SliceGate: fail closed on unknown check methods

### P1 — gate does not correlate packet with executor identity
- **Invariant:** the executor facts being validated must belong to the packet
  being dispatched; otherwise the gate validates the wrong team.
- **Evidence:** `SliceGate.swift:18` — `evaluate(packet:executor:)` takes the two
  as independent arguments; `SliceGate.swift:44-54` validates `executor` with no
  reference to `packet` (no `packet.executorTeamId == executor.teamId` check).
- **Impact:** A caller that passes packet A with executor B's facts gets the
  gate's blessing for packet A based on B's posture. The gate cannot detect the
  mismatch.
- **Suggested fix:** Add a correlation check (e.g.,
  `packet.executorTeamId == executor.teamId`), or move executor facts inside the
  packet so the binding is structural.
- **Suggested slice:** SliceGate: bind packet to executor identity

### P1 — gate vs runtime allowlist enforcement gap
- **Invariant:** the file is named "Danger + scope gate" and the type is
  `SliceGate`, implying scope enforcement; but the gate only checks presence of
  the allowlist, not that runtime touches stay within it.
- **Evidence:** `SliceGate.swift:33-34` (presence only); no runtime enforcement
  hook is visible in this file.
- **Impact:** A packet can declare `touchAllowlist = ["foo.swift"]` and the
  executor can touch `bar.swift` at runtime; the gate admits it. If runtime
  enforcement is missing or buggy, the gate gives false confidence that scope was
  checked.
- **Suggested fix:** Either (a) document explicitly in the doc comment that the
  gate is presence-only and name the runtime owner that must enforce
  touches-within-allowlist, or (b) add a runtime enforcement hook the gate
  requires. Do not let "scope gate" imply more than presence without saying so.
- **Suggested slice:** SliceGate: document/runtime scope enforcement contract

### P2 — `dangerFlags` reason message is unbounded
- **Invariant:** error reasons should be bounded for logging and UI display.
- **Evidence:** `SliceGate.swift:25` —
  `reason: "danger flag(s): \(packet.dangerFlags.joined(separator: ", "))"`.
- **Suggested fix:** Cap the joined output length (e.g., first N flags + ellipsis).

### P2 — empty `teamId` produces confusing reason text
- **Invariant:** error reasons should identify the failing entity.
- **Evidence:** `SliceGate.swift:45`, `:48`, `:51` —
  `"unknown executor team \(executor.teamId)"` etc. If `teamId` is empty, the
  reason reads "unknown executor team ".
- **Suggested fix:** Fall back to `"<empty>"` when `teamId` is empty after trim.

### P2 — gate trusts packet's self-reported `dangerFlags`
- **Invariant:** danger detection should not rely solely on the packet
  self-reporting its own danger.
- **Evidence:** `SliceGate.swift:22` — `if !packet.dangerFlags.isEmpty`.
- **Impact:** If a packet producer fails to populate `dangerFlags`, the gate has
  no independent danger signal and will not block. This is a producer contract,
  not a gate-logic flaw, but worth naming.
- **Suggested fix:** Document the producer contract for `dangerFlags` on
  `WorkSlicePacket`; if not already present elsewhere, consider a secondary
  danger signal (e.g., command content scan) so danger is not solely
  self-reported.

## False alarms ruled out
- **"`dangerFlags` with empty-string entries bypasses the gate":** `[""]` is a
  non-empty array, so `!packet.dangerFlags.isEmpty` is true → blocks. Safe
  (over-blocks). Not a bypass.
- **"nil `check.command` crashes the gate":** `(packet.check.command ?? "")`
  handles nil, then trim → empty → blocked. Not a crash.
- **"review packet with empty `touchAllowlist` is wrongly blocked":** the gate
  requires `executor.isMutating` (`SliceGate.swift:47-48`), so a read-only
  review executor cannot get through. The conservative block on review packets
  is by design, not a bug.
- **"`workerCount == 1` rejects legitimate multi-worker mutating teams":** per
  `Unified_Run_Model`, execution teams are exactly one worker (mutating) under
  the per-root write lock. The `== 1` check is the intended invariant, not a
  regression.
- **"check validation runs before executor validation, masking executor
  errors":** fail-fast ordering is fine; both still block. Not a correctness
  issue.
