# CR-08 — DriverConcurrencyGate spawn limits

## Summary

`DriverConcurrencyGate` is a process-wide actor that caps concurrent spawns
per driver id. The core counting invariant — at most `limit` holders per lane —
holds under correct single-acquire / single-release usage, and the FIFO handoff
(`release` resumes the first waiter without decrementing `active`) is sound.
Two real gaps remain: `acquire` has no timeout, so a holder whose `body` never
returns permanently stalls the lane (a live risk for the fragile CLIs this gate
exists to protect), and cancellation is not propagated to queued waiters, so a
cancelled seat still gets handed a slot and must run `body` before the slot
transfers. Several smaller issues (double-release underflow, first-acquire-fixes-
limit, redundant write, no `defer`, per-lane-only fairness, warm-pool scope,
lane retention) are P2.

## Findings

### P0 — None

No invariant violation or security issue found under correct single-acquire /
single-release usage. The ceiling invariant (`active <= limit`) is preserved by
the handoff: `release` resumes a waiter without decrementing `active`
(DriverConcurrencyGate.swift:57), so `active` stays at `limit` across the
transfer and only decrements when the last holder releases with an empty queue
(DriverConcurrencyGate.swift:59).

### P1 — No timeout on `acquire`; a hung holder stalls the lane forever

- **Invariant:** Liveness — a holder must eventually call `release` for the lane
  to drain. There is no timeout anywhere in the acquire→body→release path.
- **Evidence:** `acquire` suspends via `withCheckedContinuation` with no timeout
  (DriverConcurrencyGate.swift:46). `withPermit` calls `release` only after
  `body` returns (DriverConcurrencyGate.swift:69-70). If `body` never returns
  (a deadlocked CLI — exactly the failure mode this gate exists for:
  antigravity deadlocks, cursor races), `release` is never called, `active`
  stays at `limit`, and every waiter blocks indefinitely. For an overnight
  unattended run, one hung `cursor_agent`/`antigravity` process freezes the
  entire driver lane for the rest of the night with no diagnostic.
- **Suggested fix:** Add a timeout to `withPermit` (or `acquire`) using a
  `withTaskGroup` race between `body` and `Task.sleep(for:)`, or switch to a
  `CheckedThrowingContinuation` resumed by a timer. On timeout, call `release`
  and surface a `DriverTimeoutError` so the caller can mark the seat failed
  (never faked). The timeout should be configurable per driver (manifest field)
  since spawn latency varies.
- **Suggested slice:** `concurrency-gate: acquire timeout + seat-fail on expiry`

### P1 — Cancellation is not propagated to queued waiters

- **Invariant:** A cancelled waiter should not consume a slot.
- **Evidence:** `acquire` queues via `CheckedContinuation<Void, Never>`
  (DriverConcurrencyGate.swift:46-47) with no `withTaskCancellationHandler`.
  `release` resumes the first waiter unconditionally
  (DriverConcurrencyGate.swift:55, 57). When a team run is cancelled, its
  queued seats remain in `waiters` in FIFO order; each is resumed in turn as
  holders release, runs `body` (which may spawn a CLI before checking
  cancellation), then releases. For a fragile driver with `limit=1`, N cancelled
  seats serialize N unnecessary `body` invocations ahead of any live waiter.
- **Suggested fix:** Wrap the continuation in `withTaskCancellationHandler`. On
  cancellation, remove the waiter's continuation from `lane.waiters` (requires
  an identity index or `UUID` key) and resume it so `acquire` returns; have
  `withPermit` check `Task.isCancelled` after `acquire` returns and skip `body`
  (still calling `release` to keep the count honest). Alternatively, switch to
  `CheckedThrowingContinuation` and resume with `CancellationError`.
- **Suggested slice:** `concurrency-gate: cancel-aware queue removal`

### P2 — Double-release underflows `active` and breaks the ceiling

- **Invariant:** `active` reflects the true holder count.
- **Evidence:** `release` with an empty waiter list decrements via
  `max(0, active - 1)` (DriverConcurrencyGate.swift:59). The `max(0, …)` guards
  against negative `active` but not against a spurious release while a holder is
  still running. Scenario: holder A releases correctly (no waiters, `active`
  1→0), then A releases again (no waiters, `active` 0→0, clamped). A new
  acquirer now sees `active 0 < limit 1` (DriverConcurrencyGate.swift:38) and
  is admitted — but if the double-release happened while a *different* holder B
  was active (waiters temporarily empty between B acquiring and B's waiter
  arriving), `active` drops below the true holder count and the ceiling is
  violated.
- **Suggested fix:** Track an acquire-token count or assert `active > 0` before
  decrementing (crash on misuse rather than silently corrupting the count).
  Alternatively, return a `Permit` token from `acquire` that must be passed to
  `release`, making double-release a type error.
- **Suggested slice:** `concurrency-gate: permit token or assert on release`

### P2 — First-acquire-fixes-limit is a silent footgun

- **Invariant:** All callers of `acquire` for a given `driverId` agree on the
  limit.
- **Evidence:** `var lane = lanes[driverId] ?? Lane(limit: cap)`
  (DriverConcurrencyGate.swift:37). Once the lane exists, `cap` (from `limit`)
  is never consulted again. If two call sites pass different `limit` values for
  the same driver (e.g., manifest updated mid-process, or a chat path vs. a
  team path disagreeing), the second value is silently ignored with no
  assertion or log.
- **Suggested fix:** Assert `lane.limit == cap` on a lane hit (or at minimum
  log a warning). Better: read the limit from the manifest inside the gate
  rather than having callers pass it, so there is one source of truth.
- **Suggested slice:** `concurrency-gate: assert limit agreement on lane hit`

### P2 — Redundant write in the queue path

- **Invariant:** N/A (dead code).
- **Evidence:** `lanes[driverId] = lane` (DriverConcurrencyGate.swift:45) writes
  back a copy that was read at line 37 and not modified in the queue branch
  (the `lane.active += 1` mutation is in the early-return branch at line 39).
  The write is a no-op.
- **Suggested fix:** Delete line 45. The `waiters.append` at line 47 mutates
  `lanes[driverId]` directly.
- **Suggested slice:** `concurrency-gate: drop redundant lane writeback`

### P2 — `withPermit` does not use `defer` for `release`

- **Invariant:** `release` is always called after `acquire` succeeds.
- **Evidence:** `withPermit` calls `release` after `body` returns
  (DriverConcurrencyGate.swift:69-70) without a `defer`. This is safe today
  because `body` is `() async -> T` (non-throwing). If `body` ever becomes
  `() async throws -> T`, a throw would skip `release` and permanently leak the
  slot — the exact P1 liveness failure, now triggered by a normal error path.
- **Suggested fix:** Use `defer { release(driverId: driverId) }` after
  `acquire` returns. Future-proofs against a throwing `body` and makes the
  invariant locally obvious.
- **Suggested slice:** `concurrency-gate: defer release in withPermit`

### P2 — Multi-project fairness is FIFO per lane, not per team run

- **Invariant:** N/A (fairness, not correctness).
- **Evidence:** `release` resumes `lane.waiters.removeFirst()`
  (DriverConcurrencyGate.swift:55) — strict FIFO across all waiters on the lane.
  Two concurrent team runs on the same `limit=1` driver share one queue. A run
  that enqueues first fills the front of the queue; the second run's seats wait
  behind all of the first run's seats. There is no round-robin or per-run
  fairness.
- **Suggested fix:** If cross-run fairness matters, interleave by run id (e.g.,
  round-robin across runs in the waiter list). For the MVP, strict FIFO is
  defensible (document it); flag as P2 because the gate is process-global by
  design (DriverConcurrencyGate.swift:14-15) and the interaction is real.
- **Suggested slice:** `concurrency-gate: per-run round-robin fairness` (if needed)

### P2 — Warm-pool interaction: gate must wrap only the spawn, not the worker lifetime

- **Invariant:** The gate limits *spawns*, not active workers.
- **Evidence:** `withPermit` wraps `body` (DriverConcurrencyGate.swift:66-72).
  If a caller passes `body` that includes the worker's entire lifetime (spawn +
  use + teardown) rather than just the spawn call, the permit is held for the
  worker's full life — defeating warm-pool reuse, since a reused worker never
  re-enters `withPermit` and a re-spawned (crashed) worker must queue behind
  any long-running holder. For `limit=1` drivers, this serializes the entire
  warm pool to one active worker.
- **Suggested fix:** Document at the `withPermit` call site that `body` must be
  the spawn only (process start), not the worker's lifetime. The warm pool
  should acquire the permit for `Process.run` and release immediately after the
  process is launched, holding the worker outside the gate. (Warm-pool code not
  inlined — conceptual finding for the caller.)
- **Suggested slice:** `concurrency-gate: document spawn-only body contract`

### P2 — Lanes are never removed from the dictionary

- **Invariant:** N/A (bounded retention).
- **Evidence:** `release` decrements `active` to 0 but never removes the lane
  from `lanes` (DriverConcurrencyGate.swift:58-61). Empty lanes persist for the
  process lifetime. This is bounded by the driver manifest (a fixed set of
  driver ids), so it is not a real leak — but if driver ids are ever generated
  dynamically (e.g., per-session), the dictionary grows unbounded.
- **Suggested fix:** Optionally remove the lane when `active == 0 && waiters.isEmpty`. Low priority given the fixed manifest.
- **Suggested slice:** `concurrency-gate: evict empty lanes` (optional)

## False alarms ruled out

- **Handoff double-count:** `release` resumes a waiter without decrementing
  `active` (DriverConcurrencyGate.swift:57), so `active` stays at `limit` across
  the transfer. The resumed waiter inherits the slot; no double-count. ✓
- **Negative `active`:** `max(0, active - 1)` (DriverConcurrencyGate.swift:59)
  prevents negative `active` on the no-waiter path. (The double-release *ceiling*
  break is flagged separately as P2, but the value itself never goes negative.) ✓
- **`withCheckedContinuation` body race:** The body closure runs synchronously
  within the actor's isolation before the suspension point, so
  `lanes[driverId]?.waiters.append(cont)` (DriverConcurrencyGate.swift:47) is
  race-free — no concurrent mutation between the read at line 37 and the append. ✓
- **`release` not reached under normal control flow:** `body` is non-throwing
  (DriverConcurrencyGate.swift:66), so `withPermit` always reaches `release`
  (line 70) unless `body` hangs (flagged as P1 timeout) or the task is
  cancelled mid-`body` (in which case `body` still returns and `release` runs). ✓
- **Lane-creation race:** The actor serializes `acquire`, so two concurrent
  first-acquires cannot race on `lanes[driverId] ?? Lane(limit: cap)`
  (DriverConcurrencyGate.swift:37). The first to execute creates the lane; the
  second finds it existing. ✓
- **`limit` clamping:** `max(1, limit)` (DriverConcurrencyGate.swift:36)
  ensures a `limit` of 0 or negative does not create a zero-capacity lane that
  would deadlock every acquirer. ✓
