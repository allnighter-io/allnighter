# CR-04 — CheckRunner subprocess boundary

## Summary

`CheckRunner.run` executes the repo-declared check command via `/bin/sh -c` in the
repo root, with a 300s default timeout, and reduces stdout/stderr to a 4 KiB tail.
The skipped-vs-passed logic is correct on every branch, and the tail truncation has
no off-by-one or Unicode-splitting bug. The security-relevant properties (shell
execution, full env inheritance) are design decisions owned by the repo trust model
in `Unified_Run_Model.md`, not defects in this file — so there is **no P0 against
CheckRunner itself**. The real findings are a missing cancellation-propagation path
(P1) and a few API/perf nits (P2).

## Findings

### P0 — None in CheckRunner

No P0 invariant or security defect lives in `CheckRunner.swift`. The two
security-adjacent properties are design, not bugs:

- **Shell execution of `check.command`** is intentional: the check is *repo-declared*
  and the whole string is meant to be a shell script. `CheckRunner` does not
  concatenate any untrusted data into the command — it passes the repo's string
  verbatim to `sh -c` (CheckRunner.swift:42-43). The trust boundary is upstream
  (whether this repo is allowed to run mutating/executing teams at all), owned by
  the run model, not by this layer. Adding a "sandbox" here would break the feature.
- **Full env inheritance** (`ProcessInfo.processInfo.environment`, CheckRunner.swift:45)
  is expected for a "run the repo's test command" primitive (tests need `PATH`,
  credentials, etc.). Tightening it is a trust-model decision, not a CheckRunner fix.

Both are noted again under P2 as hygiene, but neither is a P0 invariant violation
*in this file*. Flagging "security P0" as requested: **none found here** — the
security boundary belongs to the caller's repo-trust decision.

### P1 — `run` does not propagate Task cancellation to the subprocess

- **Invariant:** An async `run` that spawns a bounded subprocess should release the
  subprocess when the owning Task is cancelled, not just when the wall-clock timeout
  fires.
- **Evidence:** CheckRunner.swift:31-35 (`run` is `async`, no `try Task.checkCancellation()`
  or `withTaskCancellationHandler`); CheckRunner.swift:41-48 (the only await is
  `commandRunner.run`, which `run` awaits unconditionally for up to `timeout`).
- **Why it matters:** If the caller's Task is cancelled (user cancels the run, a
  higher-level supervisor cancels the slice, or a parent timeout fires), `CheckRunner.run`
  will keep awaiting `commandRunner.run` until either the subprocess exits or the
  300s default timeout elapses. If `CommandRunner` itself does not bridge Swift
  cancellation to `Process.terminate()`, the child can outlive the cancelled run — a
  zombie/responsiveness hazard and a quiet quota-spend leak. This cannot be confirmed
  or fixed from `CheckRunner.swift` alone (CommandRunner is not inlined), so the
  finding is on CheckRunner's contract surface: it does not handle cancellation
  itself and does not document a cancellation guarantee from `CommandRunner`.
- **Suggested fix:** Either (a) wrap the `commandRunner.run` await in a
  `withTaskCancellationHandler` that signals cancellation to `CommandRunner` (requires
  a cancellation-aware CommandRunner API), or (b) document on `CheckRunner.run` that
  cancellation is the caller's responsibility and that `CommandRunner.run` must
  terminate the child on Task cancellation. Do not add a `try Task.checkCancellation()`
  between spawn and await — that would orphan an already-spawned child.
- **Suggested slice:** "CheckRunner: propagate Task cancellation to CommandRunner subprocess"

### P2 — Skipped guiFixture/userObservation returns `exitCode: 0`

- **Invariant:** A skipped result should not expose a success-looking `exitCode` to
  consumers that check `exitCode == 0` directly.
- **Evidence:** CheckRunner.swift:55-56 (`case .guiFixture, .userObservation: return
  .init(exitCode: 0, skipped: true)`); contrast the empty-command skip path at
  CheckRunner.swift:38-40 which leaves `exitCode: nil`.
- **Why it matters:** `passed` (CheckRunner.swift:18) correctly includes `!skipped`,
  so `passed` is `false` here — no bug *through* `passed`. But the public `exitCode`
  field is `0`, so any consumer that reads `exitCode == 0` instead of `passed` will
  see a false success. The two skip paths are also inconsistent: one yields `nil`,
  the other yields `0`.
- **Suggested fix:** Return `.init(exitCode: nil, skipped: true)` for the
  `.guiFixture, .userObservation` branch to match the empty-command skip path and
  remove the ambiguity.
- **Suggested slice:** "CheckRunner: use nil exitCode for all skipped results"

### P2 — `tail` double-traverses large output via `count` + `suffix`

- **Invariant:** The tail cap should be cheap to compute even for very large stdout.
- **Evidence:** CheckRunner.swift:62 (`guard trimmed.count > stdoutTailLimit`) and
  CheckRunner.swift:63 (`String(trimmed.suffix(stdoutTailLimit))`). `String.count` and
  `String.suffix(_:)` are both O(n) over the whole string for a non-random-access
  `String`.
- **Why it matters:** The `count` guard is intended as an optimization (avoid copying
  when small), but `count` is itself O(n), so for large output the string is traversed
  twice. This is a minor perf nit, not a correctness bug — the result is correct.
  Bounded only if `CommandRunner` caps stdout/stderr before returning; that contract
  is not visible here.
- **Suggested fix:** Drop the `count` guard and always take `String(trimmed.suffix(stdoutTailLimit))`
  — `suffix(maxLength)` already returns at most `maxLength` characters and avoids the
  separate O(n) `count` pass. Or, if `CommandRunner` does not cap output, cap there
  instead.
- **Suggested slice:** (optional) "CheckRunner: drop O(n) count guard in tail"

### P2 — Full parent environment inherited by the subprocess

- **Invariant:** A subprocess running repo-declared code should receive the minimum
  environment it needs, not the entire app environment.
- **Evidence:** CheckRunner.swift:45 (`env: ProcessInfo.processInfo.environment`).
- **Why it matters:** Every env var the Allnighter app carries (including any API keys
  or tokens loaded into the process) is exposed to the repo's check script. For a
  trusted user repo this is acceptable and often required; it is broader than necessary
  and widens the blast radius if a repo is ever run that is not fully trusted. This is
  a hygiene note, not a defect — the trust decision is the caller's.
- **Suggested fix:** No change to CheckRunner for the MVP trust model. If a future
  trust tier is added (e.g., untrusted repos), route an env allowlist through
  `WorkSlicePacket.Check` or the run model rather than special-casing it here.
- **Suggested slice:** (deferred — trust-model decision, not CheckRunner)

## False alarms ruled out

- **"Shell injection via `check.command`":** Not a CheckRunner defect. `check.command`
  is repo-declared and is *intended* to be a shell script; CheckRunner passes it
  verbatim to `sh -c` (CheckRunner.swift:42-43) without concatenating any untrusted
  data. There is no injection vector *introduced* by this file. The trust boundary is
  whether the repo is allowed to execute at all, owned by `Unified_Run_Model.md`.
- **"Skipped is reported as passed":** Ruled out. `passed` is defined as
  `exitCode == 0 && !timedOut && !skipped` (CheckRunner.swift:18), so `skipped == true`
  forces `passed == false` on every skip path (empty command at :38-40 with `exitCode: nil`;
  guiFixture/userObservation at :55-56). Verified all branches.
- **"Tail off-by-one":** Ruled out. `guard trimmed.count > stdoutTailLimit` returns the
  full string at exactly the limit; `suffix(stdoutTailLimit)` returns the last
  `stdoutTailLimit` characters above it (CheckRunner.swift:62-63). Result is at most
  `stdoutTailLimit` characters with no off-by-one.
- **"Tail splits Unicode graphemes":** Ruled out. `String.suffix(_:)` operates on
  `Character` (graphene cluster) boundaries, so no multi-byte scalar is split.
- **"cwd wrong":** Ruled out. `workingDirectory: repoRoot` (CheckRunner.swift:46) runs
  the check in the repo root, matching the run model.
- **"Timeout not propagated":** Ruled out at this layer. `timeout` is forwarded to
  `commandRunner.run` (CheckRunner.swift:47) and `result.timedOut` is propagated into
  `CheckResult.timedOut` (CheckRunner.swift:53). Whether the child is actually killed
  on timeout is a `CommandRunner` contract concern, not visible here.
