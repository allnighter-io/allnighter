## ⛔ What is DEAD — and why it stays dead (share this with mentors)

Two earlier ideas were cut after the founder's review. They were **100x more
complex than this problem needs.** Do **not** reintroduce them.

### OCR is DEAD — rejected, not deferred

- **Where it came from:** an earlier draft wanted to pull the text off an attached
  screenshot to "seed the content" for redesigns.
- **Why it's wrong:** Apple Vision OCR is genuinely bad on UI screenshots (small
  labels, icon-glyphs-as-text, stylized fonts, status-bar chrome) — the founder has
  used it extensively and it fails. Worse, it solved a problem we don't have:
- **The kill shot:** the models **see**. The image engines look at your screenshot
  natively and improve it. **LLM image recognition replaces OCR entirely** — better,
  free, and already how you actually work. There is nothing OCR provided that the
  multimodal models don't do better. *We never read pixels for text; we hand the
  model the image.*

### HTML rendering is DEAD — rejected, not deferred

The earlier draft made the **coding CLIs** (Claude Code, Grok, Codex) emit
self-contained HTML, then built a pipeline to render that HTML into pictures so the
board could show them. That single premise dragged in an enormous tail:

- a headless **WKWebView render harness** + a Chromium fallback,
- a strict **"self-contained HTML" dispatch contract** fought across heterogeneous CLIs,
- a synthesized **content fixture** (to make rendered HTML comparable),
- **pHash / DOM divergence** measurement + automatic **rerolls**,
- **hermetic-network** blocking, bundled Tailwind, and a pixel-**fidelity gate**.

**Why it's all dead:** your subscriptions already include **image engines** —
**Grok Imagine, Gemini (Nano Banana Pro), ChatGPT's image engine** — that emit
finished design images **directly, for free**, and are **better designers** than a
coding agent writing Tailwind. So:

> **Don't make coding agents cosplay as designers and then build a rendering
> pipeline to look at their homework. Let image engines design. Let coding agents
> build.** Each does the thing it is actually good at.

Killing HTML deletes the **entire** list above. The **image is the unit** — already
a picture, already comparable, no render step, no fixture, no pHash, no gates.

**The honest tradeoff (state it, don't hide it):** the design team's immediate
output is an **image** — concept art, not shippable code. We traded **data-identical
layout comparison** (the dead fixture/render machinery) for **speed to real design
range** — a conscious choice, not an oversight. And **code still happens** — at the
**Build step**, when you pick an image and an agent implements it (Design2). Image
engines design; coding agents build; nobody is forced to be what they're bad at. This
is exactly your real workflow today (you get images from ChatGPT/Gemini and they're
amazing) — plus **range** (a team, not one shot) and a **zero-paste path to code**.

**Why the image→code handoff isn't scary (the ICP point):** our user is **redesigning
a screen whose code already exists.** Someone handing over a screenshot and saying
"build this from nothing" is **not our ICP.** So the Build step is rarely "invent a
component from a picture" — it's **"restyle this *existing* file to match this
image,"** with the file's current source + the repo's tokens handed to the agent
alongside the image. Constrained edit, not generative guesswork. (Design2.)

## The Loop (the whole product)

```text
pick the Design chip  ·  attach a screenshot ("improve this")  ·  optional prompt
-> Allnighter fans the screenshot + each design persona out to the IMAGE ENGINES
   you already pay for (Grok Imagine, Gemini Nano Banana Pro, ChatGPT image, ...)
-> each returns a finished design image; the BOARD shows them side by side, same scale
-> you look first, you pick the one you love (your eyes decide)
-> "Build this" -> you choose which CLI implements it (just like the build team)
-> that coding agent reads the chosen image + builds the real code in your repo
No OCR. No HTML render pipeline. No copy/paste.
```

Fan out → board → pick → build. The design module owns only the first three; the
fourth is Lane 1's executor dispatch (RB4), reused.

## Architecture: two engines, each to its strength

| Job | Who does it | Why |
| --- | --- | --- |
| **Design** (produce options) | the **image engines** (Grok Imagine / Gemini / ChatGPT image), one per design persona | purpose-built to make things look great from a screenshot; free under your subscriptions |
| **Decide** (pick the winner) | **you** | taste is yours; the board is the first thing you see, before any AI voice |
| **Build** (turn it into code) | a **coding CLI you choose** (Claude Code / Codex / Grok / …) | coding agents are great builders; they read the chosen image and implement it |

The design workers need **image generation**; the build step needs an agent that can
**read an image**. Both are capabilities we **verify on-device** (Doctor flags), not
assume.

## Product Laws

- **Image engines design; coding agents build.** Never force one to be the other.
- **The board is the first truth surface.** You see the options before any AI
  verdict. Your eyes decide.
- **You pick; AI advises.** Any "lead designer" critique is advisory and speaks
  *after* you've looked (Design2). It never casts the vote.
- **The image is the unit.** No render step, no HTML contract, no content fixture.
  Workers emit images; the board shows them.
- **Zero marginal cost.** Only the image engines you already pay for via
  subscription. No API keys, no paid image gen, nothing uploaded to a third party
  beyond the CLIs you already use.
- **Code comes from the build step.** The design team's output is images; "Build
  this" turns the chosen image into code via a CLI you select (RB4).
- **Capabilities are verified, never assumed.** `canGenerateImages` (design workers)
  and `canReadImages` (build/critique) are Doctor-checked — a **new verified
  capability** exactly like headless-CLI vs. manual-paste was. Missing → honest skip
  or fallback, never a silent failure.
- **No silent mode switch.** Design mode is the Design chip (or a result-side
  confirm), never auto-flipped.
- **Shape before commit.** Image generations are $0 in *dollars* but may hit provider
  limits. The composer shows the requested **output count** and which engine each
  worker routes to (`WorkOrder.designSummary`) — before you commit. No quota-risk
  forecasts.

## Personas (light — range is the product)

Range comes from **different image engines × a few persona prompts**. Personas are
**one-line editable style directions**, not structural essays:

| Persona | Direction (appended to the prompt) |
| --- | --- |
| `minimal` | restraint, whitespace, type-led; strip the noise |
| `bold` | high contrast, big type, opinionated color |
| `editorial` | break the generic SaaS look; magazine/dense — while staying recognizably the same screen |
| `on_brand` | match the product's look (palette/type from the screenshot or a brand reference) |

Default = 3–4 options spread across engines × personas. The user can edit, add, or
fork a persona. If options come back too similar, the user clicks **"more / re-roll"**
— no automated divergence subsystem (that died with HTML).

## Detection

- **Prompt-side (v1):** a Design chip in the composer; attach a screenshot. The user
  tells us — no fragile classifier.
- **Result-side (later):** if a run's results are images, offer "view as a board?"
- **Mixed prompts** are out of scope; the user picks the chip.

## Artifact Contract

`run.json` is truth; files are derived.

```text
run_<id>/
  design_request.json     # prompt + persona set + attached screenshot ref + target shape (mobile/desktop)
  screenshot.png          # the attached "before" (if any); shown, never OCR'd
  option_<workerId>.png     # the generated design image per worker (the unit)
  board.json              # ordered gallery: workerId, engine, persona, imagePath
  chosen_option.json      # the human pick + rationale (logged for taste memory)
  design_build_brief.md   # DesignImplementationBrief: chosen image + existing target source + repo tokens (Design2)
  bundle.md               # composed view
```

Generated images are always **normalized to local PNGs** in the run folder (even when
a CLI returns a URL or base64). Images are referenced by path; the build context reads
them in place (RB4 context-exclusion law).

## Design Activation Gate (run before trusting the machinery)

The earlier gate evaluated render comparability — dead. The new gate is simpler and
about the only things that matter now. **Run it against the founder's real driver
manifests/CLIs before any Design1 code beyond the core models** (a throwaway image-
capture spike is enough — don't build the polished board first). Use **three real
prompts** (a screenshot redesign, a greenfield screen, and a "make this not look like
AI slop"):

1. **Capability (existential).** At least one subscription CLI generates an image
   **headlessly, at $0**. Record the **exact invocation path and how the image
   arrives** — a PNG written to a path, a URL in stdout that must be fetched+saved, or
   base64 — not just the CLI name. "The model exists in the product somewhere" does
   **not** count; "headless at $0" does. The image Doctor probe is a **separate,
   quota-aware** check (a tiny test gen), never folded into everyday text Doctor.
2. **Greenfield path.** Confirm whether image generation works **without an input
   image** (text-to-image), since it may be a different flag/worker than redesign
   (image-to-image). If not, v1 may require a screenshot — better than a broken
   greenfield Works Test.
3. **A board you'd pick from.** **≥2** options (target 4 when enough
   `canGenerateImages` workers exist) come back side by side, different enough that a
   non-designer picks a favorite in < 60s.
4. **Build works.** "Build this" hands the chosen image **+ the existing target file's
   source + repo tokens** to a coding CLI that **reads the image** and produces a
   plausible *edit* of the existing code (Design2's redesign framing). A thin pass —
   the executor received the image path and referenced it — is enough at the gate.

If no CLI generates images headlessly at $0, **stop** — the premise needs a different
invocation path (the sanctioned later answer is **BYOK**, § Deferred — **not** browser
automation, which is just the dead render-tail in a new costume).

**Live board-capability proof (2026-06-15, `swift run prove-cli --design <engine>`):** all
three engines produced a **real, validated local PNG** through the actual manifest →
`DesignImageRunner` → capture/normalize/magic-byte pipeline at $0 — both arrival modes
(`prompt_directed`: Grok, Codex; `stdout_path`: Antigravity). **Gate finding:** in
headless `--print`, agy first returned a *markdown design doc*, not an image; a forceful
prompt ("create an actual raster PNG, not markdown/HTML; reply with ONLY the .png path")
makes it fire its image tool reliably — now baked into the antigravity manifest template.
Remaining gate items (UI board run with real images + a real build) are app-driven and
spend quota — the founder validates those in-app; the engine pipeline itself is proven.

**Capability finding (2026-06-15):** the bench sorted into the two roles cleanly —
three image engines for the **design** workers, **Claude Code** as the **build**
implementer (strong coder + reads images; can't generate them). **Gemini's driver is
Antigravity CLI** (`agy`), not the legacy gemini-cli (install:
`curl -fsSL https://antigravity.google/cli/install.sh | bash`); this also promotes
Gemini from `manual_paste` to a **real headless worker in the *text* lane** — a
separate, ready-to-wire slice (`agy --print "{{prompt}}" --model "{{model}}"
--dangerously-skip-permissions`), tracked outside the design module.

**Pinned image-gen invocations (2026-06-15) — the common contract:** every engine
runs image gen as an **agentic tool call** behind an **auto-approve** flag, **writes a
local file** (PNG/JPEG — never base64/URL), and **reports the path in stdout**:

```text
Grok:        grok -p "<designPrompt>. Save the final image to <runDir>/option_<worker>.jpg
                      and reply with the absolute path only." --yolo --output-format json --cwd <runDir>
             → writes to ~/.grok/sessions/.../images/N.jpg; path in JSON .text (honors explicit save path)
Antigravity: agy --print "<designPrompt>. Generate an image." --dangerously-skip-permissions --print-timeout 10m
             → writes PNG to ~/.gemini/antigravity-cli/brain/<session>/<name>.png; path embedded in stdout markdown
             → opaque dir: PARSE the path from stdout and copy into the run folder
Codex:       codex exec -C <runDir> --skip-git-repo-check
                  '<designPrompt>. Use the built-in image generation tool.
                   Save the final PNG to <runDir>/option_<worker>.png and reply with the absolute file path only.'
             → writes file (default ~/.codex/generated_images/... if no path); honors explicit save path
```

Grok & Codex **honor an explicit save path**; Antigravity writes to an opaque
artifact dir, so for it we **parse + copy**. `--yolo` / `--dangerously-skip-permissions`
/ `--skip-git-repo-check` are **required** for unattended runs (image_gen triggers a
permission prompt otherwise). Capture each run's `sessionId` (Grok JSON / agy `-c` /
codex resume) — it's the handle for "more like this" (image edit on resume).

## Moat

claude.ai/design and ChatGPT give you **one** pretty image and **no path to code**.
You get: a **team** (range across engines × personas), **your taste** as the
verdict, and a **zero-paste jump from the chosen image to real code** via the CLI you
choose — in the **same tool as your build team**. Image engines design, coding
agents build, you decide, and you never leave Allnighter.
